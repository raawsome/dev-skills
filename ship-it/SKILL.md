# Ship-it — router-orchestrator with nesting

You are the top-level orchestrator. You route, then run one phase at a time. Each phase is one **phase lead** subagent (`Agent` tool). Briefs carry pointers (`<scratch>/state.md`, map URL, spec URL, ticket IDs, SHAs), never pasted bodies. A subagent may run in the background: wait for its result notification before acting on it.

Run in the main conversation: only it can talk to the user. Ship-it needs a git repository with a configured issue tracker (Route step 1).

## Depth protocol (binding)

Chain: main session (depth 0) → phase lead (depth 1) → leaf (depth 2). This fits `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` 3 (the default from v2.1.219; pin it in settings `env` on older builds) with one layer spare; in OpenCode the same 0→1→2 budget is `subagent_depth: 3`, so pin that instead. Briefs use the depth words the cited skills read (research §fanout-depth). Phase lead briefs say `depth: top`: each lead is the top-level invocation of the skill it follows, and it fans out only where this section allows. Every leaf brief says, verbatim: "depth: child (leaf): spawn nothing. Where a skill says to fan out, do that work serially yourself. If you need the user, return `NEEDS-USER [confidence: high|medium|low]: <question>`; if the sketch you are filling needs a scrap or redesign (architect Phase D drift or Phase E), return `SCRAP: <evidence>`; your lead handles both."

- Only the main session and phase leads spawn subagents, and a lead spawns only the leaves its phase section names (Phase 2 and 3 leads spawn nothing).

## Human-in-the-loop relay (binding)

Only you (the main session) talk to the user. You never answer a `confidence: low` grilling question or pick its option for the user. You relay `low` verbatim; `high`/`medium` take the recommended answer with an `ASSUMED` log line.

Relay loop (every phase):
1. Launch the phase lead (`Agent`) and record its id. The brief points at `<scratch>/state.md` (`<scratch>`: Route step 3), names its log, `<scratch>/relay-<phase>[-<ticket-id>].md` (`<phase>`: `sharpen`, `spec`, `tickets`, `implement`, `review`), and carries the contract below.
2. `ROUND`, `PROTOTYPE-READY`, `CHECKLIST` and `DRAFT` end your turn. If a question is a fact (answerable from code, docs, ADRs, the tracker; never for infrastructure failures), `SendMessage` "fact: look it up: <question numbers>" and wait for the corrected message (OpenCode: `task` with the same `task_id` and text); at most once per question, then print it as is. Otherwise print it verbatim and wait for the reply; `AskUserQuestion` may collect it when the round has at most 4 questions, each with discrete options, recommended first (OpenCode: no `AskUserQuestion`, so print the same numbered options, recommended first, as plain text).
3. `SendMessage` the same id: `USER ANSWERS (<tag>[ <n>]):` plus the reply verbatim, partial or off-topic included (OpenCode: `task` + that `task_id`, same message; if it no longer resumes, relaunch from its log per step 5). "Yes" accepts the recommended answers.
4. `WAITING` is not a miss: end your turn, no nudge. When the lead's completion notification arrives and the last message you received from it was `WAITING` or untagged, read its `relay-<phase>[-<ticket-id>].last.md` and act on that as its message. Still no tag: `SendMessage` "end with one of ROUND, PROTOTYPE-READY, CHECKLIST, DRAFT, DONE, WAITING; if you cannot proceed, say so in a CHECKLIST or ROUND" (OpenCode: `task` + `task_id` with the same text, or relaunch per step 5 if it no longer resumes). At most 2 nudges per lead; a third miss halts the phase: print the lead's last message verbatim and ask the user, then `SendMessage` the reply to the same id or relaunch per step 5.
5. Repeat until `DONE`. If `SendMessage` fails or the agent is gone, stop the old id if it still runs (`TaskStop`), then launch a fresh lead with the log path, "resume from the log", and any `USER ANSWERS` not yet delivered. (OpenCode has no `SendMessage` or `TaskStop`: resume the lead with `task` + its `task_id`; if it cannot resume, launch a fresh lead from the log exactly as here — the fresh lead's log-based resume, claim check and tracker search are unchanged.) The fresh lead checks ticket status and worktrees before relaunching any leaf. It resumes the ticket its log names even though that ticket is already claimed: a claim with a log is resumable, not someone else's. Phases 1-3: before any create (map, ticket, spec, tickets), the lead first reads the ids in `state.md` and its log, then searches the tracker for what already exists (GitHub `gh issue list --state all --search "\"<title>\" in:title" --json number,title,labels`; GitLab `glab issue list --all --search "<title>" -O json`; local: the files under `.scratch/<slug>[-map]/`; tickets also by their spec parent, the map by `wayfinder:map`; search lags, so recorded ids win). It reuses what exists, creates only what is missing, and re-runs labels, sub-issue links, blocking edges and the second-pass id rewrite on every item of a partial set, then grep-clean.

`SendMessage` only inside one phase or wayfinder ticket; each new phase or ticket gets a fresh lead. In OpenCode `WAITING` ends the lead's turn (no live re-entry): re-invoke its `task_id` when the background completion notification arrives.

Contract, verbatim in the brief: "Mode: <mode from state.md: standard|important-only>. Where a skill says to ask, confirm with, or wait for the user, end your turn instead with the matching tag. Do your own fact reads; never fan out for them (overrides grilling's sub-agent dispatch; a research ticket's `research` angles are not fact reads). Never answer a `confidence: low` decision yourself in `standard`; in `important-only` never answer an IMPORTANT `low` yourself (cite the matching IMPORTANT bullet in the log; missing `confidence` = `low`; no matching bullet = routine). IMPORTANT parks at every confidence (public API/schema/wire/external-contract even when `medium`/`high`: relay it). For routine `high`/`medium` take the recommended answer and log `ASSUMED: <question> -> <answer> (confidence: <high|medium>)`. A leaf you launched that needs the user returns `NEEDS-USER [confidence: high|medium|low]: <question>`; one that returns `SCRAP` hands you the architect Phase D or E re-arena, which you run (its re-arena runners are your leaves). For `NEEDS-USER`, park that work, keep the rest moving; auto-take routine with an `ASSUMED` log line, and when nothing else can move, end your turn with one `ROUND` holding every parked IMPORTANT question. Append every round, answer and your DONE summary to the log before ending your turn, and each created issue's URL/ID (map, spec, tickets: draft number -> ID) to `state.md` the moment its create returns. Every turn-ending message starts with exactly one tag, and you first overwrite `<your log minus .md>.last.md` with it verbatim:
- `WAITING <leaf ids>`: leaves still run and nothing else can move; you are re-invoked when they finish.
- `ROUND <n>`: `FACTS RESOLVED` (one line each, with evidence: path, ADR, command), then only `confidence: low` frontier questions in grilling's format plus a `confidence: low` line per question. Rate every frontier question `confidence: high|medium|low` on the recommended answer; `high`/`medium` never relay: take the recommended answer, append `ASSUMED: <question> -> <answer> (confidence: <high|medium>)` to the log, and continue. Also use it for any stop-and-ask a skill names: wayfinder finding no fog, a stalled ticket graph, a sign-off checkpoint. An infrastructure failure one retry won't fix (tracker or CLI unusable, a leaf returns garbage, you cannot proceed): `CHECKLIST` when only the user can fix it (auth, missing `gh`/`glab`, label permission; facts to report back: the failing command and its error), else `ROUND` with one question and `confidence: low`; never a fact bounce. Hard-stop `ROUND`s (stop-and-ask, infra, Phase 4 completion, Interrogate size, UNPROVEN wire-format, triple-red) always relay regardless of confidence, except where Important-only mode lists them as routine.
- `PROTOTYPE-READY`: how the user runs it and what to judge.
- `CHECKLIST`: steps only the user can take (accounts, credentials, dashboards), and the facts to report back. If the steps capture any value or span 2+ stages, follow `wizard` (script at `<scratch>/wizard-<name>.sh`) and list its run command; the user replies `done` or variable names, never values, so none enter the relay log.
- `DRAFT`: proposed seams or slices, plus the draft path. Nothing published.
- `DONE`: settled decisions, ASSUMED list (high/medium-confidence auto-taken, with confidence noted; in `important-only` also routine low auto-taken, with reason), artifact pointers."

## Important-only mode (opt-in)

Invoke as `ship it important-only`. Record `mode: important-only` in `<scratch>/state.md` and every lead brief. Default `standard` is low-frontier questions plus structural gates (`slug` resume, GATE 1-3, between-ticket go-ahead, Phase 4 completion, Interrogate size, UNPROVEN wire-format); `important-only` filters both by the list below.

In `important-only`, relay only IMPORTANT; otherwise take the recommended answer, append `ASSUMED: <question> -> <answer> (routine low; <reason>)` to the log, and continue. When unsure, treat as IMPORTANT but cite the bullet.

IMPORTANT (always relay as `ROUND`/`CHECKLIST`/`PROTOTYPE-READY`/`DRAFT` as usual, at any confidence):
- Security, auth, permissions, secrets, crypto; data deletion, data loss, privacy; concurrency/lifecycle UNPROVEN touching those.
- Public API, schema, wire-format, external contract, migration, shared fixtures; any UNPROVEN wire-format fact (merge-blocking). New/edited ADR; unconfirmed test seam; in-place change or bare decision.
- Spend, billing, external accounts, credentials, human-click dashboards (`CHECKLIST`, wizard values). Try AFK first; HITL only when genuinely human-only.
- Hard-to-reverse + surprising + real trade-off: merge/rebase trade-off resolution, every architect Phase C trigger (disputed Interrogate findings, 2 rounds exhausted, ADR contradiction, naming/permissions/data-loss/cost/shipped-UX), second scrap.
- Blocks all progress: stalled graph, empty frontier with blocked tickets, sign-off checkpoints where destination/interface changes.
- GATE 1 destination confirm (never auto-approved). Gaps needing a choice: Phase 4 completion with non-trivial gaps (fix/drop/rewire vs proceed), triple-red gaps, fix red after three tries. Docs/non-functional gaps touching no public surface are routine.
- `PROTOTYPE-READY` only when ≥2 viable options or user-visible UX meaning; copy/label tweaks are routine.

Routine (auto-take, never end the turn):
- GATE 2/3 `DRAFT` approvals only when ≤1 new seam and no shared-fixture touch: publish, log `ASSUMED: GATE <n> auto-approved (important-only)`, keep the draft file for post-hoc correction (do not delete). Otherwise IMPORTANT.
- Slug exists: auto-resume only when recorded `mode`/path/destination match the invocation; else IMPORTANT. No `state.md`: rebuild from logs, continue as `<slug>-2`.
- No-fog → Path B switch: auto-yes only when destination unchanged and no map tickets exist; else IMPORTANT.
- Between tickets (overrides Phase 1 "continue on the user's go"): continue, name closed/next at the next stop.
- Interrogate size prompt: auto-no only when triage shows no auth/wire/shared-code signal, log `ASSUMED: interrogate declined (important-only)`; else IMPORTANT.
- Phase 4 with zero gaps: skip the completion `ROUND`, go `DONE` with landed counts.
- Leaf `NEEDS-USER [confidence: high|medium|low]`: the lead tags importance per this list; routine auto-takes with `ASSUMED`, only IMPORTANT parks into a `ROUND`.

Report in `important-only`: print every `ASSUMED` line grouped by phase at the end of `report.md`; `DONE` carries landed/gapped counts even when the completion `ROUND` is skipped.

## Route (in-session, no subagent)

Read the target SKILL.md before each phase; summaries here are a cache.

1. Preconditions. If one fails, stop and tell the user what's missing:
   - `git rev-parse --show-toplevel` succeeds. With no repository, ship-it doesn't apply: point the user at the `grill-me` skill.
   - `docs/agents/issue-tracker.md` exists and names GitHub, GitLab or local markdown. Any other tracker's doc must give the commands to create, fetch, comment on, label, close and block issues (Path A also: child link, claim, frontier query, per wayfinder's Wayfinding operations). Otherwise the user invokes the `setup-matt-pocock-skills` skill or adds the missing commands. This overrides wayfinder's local-markdown fallback.
2. Pick exactly one sharpening path:
   - Huge, foggy, greenfield, destination unclear, larger than one session holds → Path A (`wayfinder`: chart map, work tickets until clear, merge at `to-spec`).
   - Holdable in one session → Path B (`grilling` + `domain-modeling`, what `grill-with-docs` runs; both are model-invoked, so the lead can load them).
   - Conversation already holds settled decisions (cleared map, finished grilling) → write them to `<scratch>/relay-sharpen.md` as a `DONE` summary, set `state.md` path to A if a map is cited, else B, then skip to Phase 2.
3. Fix `<slug>` now, once: the kebab-case name of the effort (also `to-tickets`' `<feature-slug>` and `implement-spec`'s `<spec>`); if `.scratch/<slug>` or `.scratch/<slug>-map` already exists from an earlier run, ask the user whether to resume it (update its `state.md`, then fresh leads per relay step 5 for the first unchecked phase in `state.md`, in Phase 1 the `relay-sharpen*` log whose last tag line is not `DONE`, else the map frontier; with no `state.md`, rebuild it from the logs) or pick a new slug. `<scratch>` is the absolute path `<repo-root>/.scratch/<slug>` in the main checkout; briefs always pass it absolute, since leaves work in worktrees. On a local tracker, Path A's wayfinder `<effort>` is `<slug>-map`, so map tickets (`.scratch/<slug>-map/issues/`) never collide with build tickets (`.scratch/<slug>/issues/`).
4. Write `<scratch>/state.md`: mode (`standard` default, or `important-only` when invoked with `important-only`), slug, path, and a checklist Route / Sharpen / Spec / Tickets / Implement / Review. Add pointers as they appear (map URL or wayfinder effort, spec URL, ticket IDs, `$INTEGRATION` and its worktree path, `BASE`, check commands, PR URL, must-clear path, gaps dir). Update it at every phase end. It is the run's todolist and its handoff between phases.
5. Labels (GitHub/GitLab only): a create with `--label` fails on a missing label. Before the first publish that needs one, create whichever of these is missing (`gh label create <name>` / `glab label create --name <name>`; an already-exists error counts as success, so no list is needed): `ready-for-agent` and `ready-for-human` (spelled per `docs/agents/triage-labels.md` when it exists; every brief carries that path, and role names in this file and the cited skills map through it), `blocked-by-gap`, plus on Path A `wayfinder:map`, `wayfinder:research`, `wayfinder:prototype`, `wayfinder:grilling`, `wayfinder:task`.

## Phases (one lead each, sequential, HITL gates hold via the relay)

Phases 1-2 rule, both paths: a lead that edits `GLOSSARY.md` or an ADR does so in the integration worktree and commits there before returning. It creates `$INTEGRATION` and its worktree per `implement-spec` step 3 if absent, and records both in `state.md`. It never commits to the default branch. While `$INTEGRATION` exists, every Phase 1-2 lead and leaf reads and edits those files in that worktree (briefs pass the path), so a later lead sees earlier edits and Phase 4 worktrees inherit them.

### 1. Sharpen (lead depth 1; research leaves depth 2)

- Path A: the lead follows `wayfinder/SKILL.md` as reference. Chart once (relay both charting grills; the brief says the destination must end in a spec for `to-spec`, and an in-place change or bare decision is a `ROUND`; if charting finds no fog, its `ROUND` asks whether to switch to Path B, and a yes sets `state.md` path to B with the charting logs counting as Path B's conversation), then one fresh lead per follow-up ticket, which creates its relay log before claiming. The charting lead's research tickets run as depth-2 leaves, each in its own worktree (push its branch only when there is a remote); each returns its answer and Decisions-so-far line to the lead (on every tracker the leaf never comments on, edits or closes the ticket; the charting lead posts the resolution comment and closes it, in the main checkout on a local tracker), which appends those lines to the map one at a time. A later research ticket's own lead may fan out `research`'s angles as depth-2 leaves. Grilling/prototype tickets run through the relay under that ticket's own fresh lead, which after the final answers arrive posts the resolution comment, closes the ticket and appends its Decisions-so-far line to the map. A prototype stays on a throwaway branch or worktree linked from the ticket by branch name (local: a line in `## Answer`); it never touches real code or main (overrides `prototype` step 6, which assumes an implementation issue), and its verdict goes in the resolution comment. Task tickets: HITL `CHECKLIST` (try AFK first; HITL only when genuinely human-only); AFK, the lead does them. Between tickets, end your turn naming the ticket that closed and the next one, and continue on the user's go (in `mode: important-only`, continue without waiting, naming at the next stop). Exit when no open tickets remain and no fog is left. An empty frontier with open tickets still blocked is a `ROUND`.
- Path B: the lead follows `grilling` and `domain-modeling`. Done when it returns `DONE` (frontier empty).
- GATE 1: show the `DONE` summary (Path A: you compile it from the map's Decisions-so-far) and ask the user to confirm the destination (Path A) or shared understanding (Path B). Phase 2 starts on a bare confirmation; a reply with any change is a correction: append `CORRECTION: <text>` to the Phase 1 log, launch a fresh Phase 1 lead from the logs with it (Path A: a new wayfinder ticket or charting re-grill; Path B: resume grilling) and re-show GATE 1. The log is finished only when its last tag line is `DONE`, so a `DONE` followed by `CORRECTION` resumes.

### 2. Spec (lead depth 1, spawns nothing)

The lead follows `to-spec/SKILL.md` as reference. Path A: the brief points at the map (`to-spec` step 1 reads it). Path B: every `relay-sharpen*.md` log is the conversation to synthesize. Publish only on approval: this overrides `to-spec` step 2's seam check and step 3; the `DRAFT` is the check. Write the draft to `<scratch>/spec-draft.md` and return `DRAFT` (seams, existing versus new, draft path). Done when the approved spec is published and its `DONE` reports the URL; record it in `state.md`.
- GATE 2 (before publication): unless `mode: important-only` with ≤1 new seam and no shared-fixture touch (then auto-publish per Important-only mode, keeping the draft file), the printed `DRAFT` is the ask. A reply with any change is a correction: relay it per step 3 and wait for a new `DRAFT`; the lead also fixes any glossary or ADR an overturned assumption shaped. On a bare approval, send one message: the reply per relay step 3, then "approved: create missing labels per Route step 5, publish one spec issue labelled `ready-for-agent`, then delete the draft last (after its record in `state.md`)". The approved seams are the run's confirmed test seams (Phase 4).

### 3. Tickets (lead depth 1, spawns nothing)

The lead follows `to-tickets/SKILL.md` as reference, running its grep-clean gate on the drafts. Do not publish yet: this overrides `to-tickets` §5. On GitHub/GitLab the spec issue (`state.md`) is the source issue, so published tickets become its sub-issues. Write one draft per ticket to `<scratch>/tickets-draft/<NN>-<slug>.md`, numbered blockers first, with `Blocked by:` written in those draft numbers and every `Both:` set to `no` (no sketch exists yet to cite; `implement-spec` step 4 arbitrates), and return `DRAFT` (slices, blocking edges, flags). Done when the approved drafts are published and `DONE` reports ticket URLs/IDs blockers-first; record them in `state.md`.
- GATE 3 (before publication): unless `mode: important-only` (then auto-publish per Important-only mode, keeping draft files), the printed `DRAFT` is the ask. Corrections and approval work as at GATE 2; the approval adds "approved: publish per `to-tickets` §5 (blockers first, `ready-for-agent`, draft numbers rewritten to real IDs in the second pass, then re-run grep-clean on each published body), then delete the drafts last (after every create and the second pass finish)".

### 4. Implement (lead depth 1; leaves depth 2)

The lead follows `implement-spec/SKILL.md` steps 1–6 as reference on `integration/<slug>` (`$INTEGRATION`); steps 7–9 belong to Phase 5. A Phase 1-2 lead may have created it already: reuse it, and if it has no commits ahead of the default ref, run `git fetch origin <default-branch>` (with a remote) and then `git -C <its worktree> merge --ff-only <default-ref>` first. At step 3 the lead records `$INTEGRATION`, its worktree path, `BASE` and the check commands in `state.md`. Its leaves (each brief carries the leaf line above plus `$INTEGRATION`, the absolute `<scratch>` and the spec URL, whose seams are confirmed): one implementer per frontier ticket (`implement-spec` step 4) and one merger at a time (step 5), briefed with the integration worktree path.
- Mergers: a merger that ends without landing resets that worktree to the pre-merge HEAD the lead recorded before launching it (`git rebase --abort` or `git merge --abort` if one is in progress, then `git reset --hard <sha>` and `git clean -fd`, never `-x`; as `resolving-merge-conflicts` step 3 expects). The lead checks `git status --porcelain` is empty before the next one, and, with a remote, after each landing pushes `$INTEGRATION` per `implement-spec` step 3. A parked merger frees the slot as if bounced and is relaunched fresh, at the back of the queue, after the answer.
- Trade-offs: a leaf hitting a merge or rebase conflict follows `resolving-merge-conflicts` and returns each trade-off it notes in its handback. The lead appends each to `relay-implement.md` at once, and copies it to `<scratch>/must-clear.md` once the ticket lands through its merger (a gapped ticket's go in its gap file).
- Flagged tickets: flag routing per `implement-spec` step 4, but the lead runs each flagged ticket's architect or arena step itself (read `architect/SKILL.md` / `arena/SKILL.md` as reference, never via the Skill tool; they are user-invoked). Runners, judge, arena's coherence reviewer and interrogate reviewers are its depth-2 leaves, grounding is read serially, and one implementer then fills the settled sketch. An architect Both-signal makes the lead write `Both: yes` with its cites and arbitrate per `implement-spec` step 4 at once; an active holder's code-arena replaces the filling implementer.
- Commits: the lead commits an arena result (`Arena: yes`, or `Both`'s code-arena) or a scaffold to a ticket branch it creates in its own worktree from `$INTEGRATION` (`Arena: yes`: from the tip SHA named in the candidates' brief, even if `$INTEGRATION` has moved, so the ff-only below holds), and records each commit SHA in `state.md`. `Both` keeps that one worktree and branch through scaffold, code-arena and verify. Candidates fork from the scaffold SHA (`Arena: yes`: the `$INTEGRATION` tip SHA, named in the brief) and never rebase. The pick lands by `git merge --ff-only` of the base candidate's branch onto the ticket branch, with grafts hand-folded and committed on top. Drift against `$INTEGRATION` is handled when the branch lands (step 5).
- Worktrees: the lead removes a worktree (`git worktree remove --force`, then `git worktree prune`) only once `git -C <wt> status --porcelain` is empty or its contents are deliberately discarded (runner and candidate worktrees after the pick and graft are committed and the synthesis note written). Their branches are deleted by arena Outputs; every other branch survives.
- Landing and red: an `Arena: yes` or finished `Both` branch lands like any implementer's (step 5). A scaffold branch is first taken at its tip by the filler, or after a first red with no implementer to message by a repair implementer. A fresh implementer after a second red takes a new branch from the recorded scaffold SHA (`Arena: yes`: arena result SHA), so the lead's commit survives and no branch is shared. This overrides `implement-spec` step 4's branch-from-`$INTEGRATION` for lead-committed tickets. The failed implementer's worktree is discarded in Phase 5.
- Bookkeeping: the lead appends `SCRAP <ticket> #n` to `relay-implement.md` per architect scrap it handles; a resumed lead counts them. It spawns the exploration subagent, or runs the swarm when `implement-spec` step 2 triggers it (read `swarm/SKILL.md` as reference, never via the Skill tool); its workers are leaves. Test seams: the spec approved at GATE 2 lists the confirmed seams, which satisfies `tdd`'s confirm step. Any other seam is a leaf's `NEEDS-USER [confidence: high|medium|low]` question (only IMPORTANT relays; routine auto-takes per relay contract and Important-only mode), and an architect checkpoint the lead hits itself is parked the same way, joining that `ROUND`.
- Write the must-clear list to `<scratch>/must-clear.md` as entries arrive. Triple-red tickets gap per `implement-spec` step 5.
- Done when every ticket is landed, gapped, `blocked-by-gap`, or waiting behind a gapped ticket, with the user told in a `ROUND` (`implement-spec` steps 5–6; in `mode: important-only` skip it when zero gaps or docs/non-functional gaps touching no public surface, going `DONE` with counts). A flag fix waiting on the user goes in that `ROUND`; it is not a reason to keep looping. On the answer, fix, drop or rewire continues the frontier (a fixed gap ticket resets to `ready-for-agent`); proceed ends Phase 4 in `DONE` with the partial set, spec left open, gaps listed in the report. `DONE` reports the PR URL (if any), must-clear path and gap paths; record them in `state.md`.

### 5. Review and close (lead depth 1; review and fix leaves depth 2)

The lead works in the integration worktree (`implement-spec` step 3; a branch can be checked out in only one worktree) and runs `dev-code-review` with `BASE` from `state.md` as the fixed point and the spec URL from `state.md` as its §2 spec source (it never asks the user for the spec); the axis reviewers and any gate reviewers are its depth-2 leaves, each briefed with the worktree path from `state.md` as its cwd. Append each leaf's output to `relay-review.md` as it returns; the Blast-radius writeup goes under `## Blast-radius` there, and that is the writeup path to report. The Interrogate size prompt is a `ROUND` question, overriding `implement-spec` step 7's log-and-continue (unless `mode: important-only` with no auth/wire/shared-code triage signal, then auto-no per Important-only mode). Then, serially:
1. Fix the review issues and every `<scratch>/must-clear.md` entry (`implement-spec` step 7); its implementer and the merger that lands the fix (step 5 gate) are leaves, and you never edit `$INTEGRATION` yourself.
