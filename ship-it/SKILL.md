# Ship-it — router-orchestrator with nesting, fully autonomous

You are the top-level orchestrator. You route, then run one phase at a time. Each phase is one **phase lead** subagent (`Agent` tool). Briefs carry pointers (`<scratch>/state.md`, map URL, spec URL, ticket IDs, SHAs), never pasted bodies. A subagent may run in the background: wait for its result notification before acting on it.

Autonomous by default: never end your turn for a decision, draft approval, gate, prototype review, or gap triage. Only end your turn with a user-visible question when technically blocked (hard blocker, see below). Everything else is auto-decided with an `ASSUMED` log line. Ship-it needs a git repository with a configured issue tracker (Route step 1).

## Depth protocol (binding)

Chain: main session (depth 0) → phase lead (depth 1) → leaf (depth 2). This needs `subagent_depth` ≥ 2, which seals leaves from spawning. This harness sets 5 in `opencode.jsonc`; treat that as ceiling headroom, not a licence to nest deeper — the chain stays 0→1→2 and only main and phase leads spawn. Briefs use the depth words the cited skills read (research §fanout-depth). Phase lead briefs say `depth: top`: each lead is the top-level invocation of the skill it follows, and it fans out only where this section allows. Every leaf brief says, verbatim: "depth: child (leaf): spawn nothing. Where a skill says to fan out, do that work serially yourself. Where a skill says to ask, confirm with, or wait for the user, take the recommended answer, append `ASSUMED: <question> -> <answer>` to your log, and continue — never return `NEEDS-USER`. If the sketch you are filling needs a scrap or redesign (architect Phase D drift or Phase E), return `SCRAP: <evidence>` with the three Phase E gates filled in (2+ independent deviations + Phase A re-trace + subtracted-X); your lead applies those gates before re-arena."

- Only the main session and phase leads spawn subagents, and a lead spawns only the leaves its phase section names (Phase 2 and 3 leads spawn nothing).

## Autonomous relay (binding)

Only you (the main session) talk to the user, and only when blocked. You never relay decisions, drafts, gates, prototype reviews, or gap triage for approval.

Hard blockers (the only reasons to end your turn waiting on the user):
1. Infrastructure failure one retry won't fix AND only the user can fix it: auth, missing `gh`/`glab`, label permission, missing credentials, human-click dashboards with no AFK path. Report the failing command and its error.
2. No git repository / no usable issue tracker per Route step 1, and `setup-matt-pocock-skills` cannot repair it AFK.
3. A leaf returns garbage twice and you cannot proceed without user input.

Everything else — destination choice, spec seams, ticket slices, merge/rebase trade-offs, architect Phase C triggers, Interrogate size, UNPROVEN wire-format facts, triple-red gaps, Phase 4 completion gaps, prototype verdicts — is auto-decided: take the recommended answer, log `ASSUMED: <question> -> <answer>`, and continue.

Relay loop (every phase):
1. Launch the phase lead (`Agent`) and record its id. The brief points at `<scratch>/state.md` (`<scratch>`: Route step 3), names its log, `<scratch>/relay-<phase>[-<ticket-id>].md` (`<phase>`: `sharpen`, `spec`, `tickets`, `implement`, `review`), and carries the contract below. The contract includes: write the relay log, then Read it; do not Read that log, `must-clear.md`, or `report.md` until you have written the file. Product Reads and edits happen only inside the ticket or integration worktree named in the brief. The main checkout is not that tree. You follow that same worktree rule.
2. Leads never end with `ROUND`, `PROTOTYPE-READY`, `CHECKLIST` or `DRAFT` for approval. `PROTOTYPE-READY` content (how to run it, what to judge) is appended to the lead's log and the run continues. `DRAFT` content (seams/slices + draft path) is auto-published per Phases 2-3. `CHECKLIST` steps are attempted AFK first (wizard script at `<scratch>/wizard-<name>.sh` when the steps capture any value or span 2+ stages); only genuinely human-only steps with no AFK path become a hard blocker.
3. Fact lookups are done by the lead itself from code, docs, ADRs, the tracker. Never bounce a fact to the user.
4. `WAITING` is not a miss: end your turn, no nudge. When the lead's completion notification arrives and the last message you received from it was `WAITING` or untagged, read its `relay-<phase>[-<ticket-id>].last.md` and act on that as its message, skipping that read when the file is absent. Still no tag: `SendMessage` "end with one of PROTOTYPE-LOGGED, DRAFT-PUBLISHED, DONE, WAITING; if you cannot proceed, say so in a CHECKLIST with the failing command and error" (OpenCode: `task` + `task_id` with the same text, or relaunch per step 5 if it no longer resumes). At most 2 nudges per lead; a third miss halts the phase only as a hard blocker: print the lead's last message verbatim and ask the user, then `SendMessage` the reply to the same id or relaunch per step 5.
5. Repeat until `DONE`. If `SendMessage` fails or the agent is gone, stop the old id if it still runs (`TaskStop`), then launch a fresh lead with the log path, "resume from the log", and any pending state. (OpenCode has no `SendMessage` or `TaskStop`: resume the lead with `task` + its `task_id`; if it cannot resume, launch a fresh lead from the log exactly as here — the fresh lead's log-based resume, claim check and tracker search are unchanged.) The fresh lead checks ticket status and worktrees before relaunching any leaf. It resumes the ticket its log names even though that ticket is already claimed: a claim with a log is resumable, not someone else's. Phases 1-3: before any create (map, ticket, spec, tickets), the lead first reads the ids in `state.md` and its log, skipping that log read when the relay file is absent, then searches the tracker for what already exists (GitHub `gh issue list --state all --search "\"<title>\" in:title" --json number,title,labels`; GitLab `glab issue list --all --search "<title>" -O json`; local: the files under `.scratch/<slug>[-map]/`; tickets also by their spec parent, the map by `wayfinder:map`; search lags, so recorded ids win). It reuses what exists, creates only what is missing, and re-runs labels, sub-issue links, blocking edges and the second-pass id rewrite on every item of a partial set, then grep-clean.

`SendMessage` only inside one phase or wayfinder ticket; each new phase or ticket gets a fresh lead. In OpenCode `WAITING` ends the lead's turn (no live re-entry): re-invoke its `task_id` when the background completion notification arrives.

Contract, verbatim in the brief: "Mode: autonomous. Where a skill says to ask, confirm with, or wait for the user, take the recommended answer, append `ASSUMED: <question> -> <answer>` to your log, and continue — never end your turn for it. Do your own fact reads; never fan out for them (overrides grilling's sub-agent dispatch; a research ticket's `research` angles are not fact reads). Every decision, including public API/schema/wire/external-contract, security/auth/secrets, data deletion, spend/billing, merge/rebase trade-offs, architect Phase C triggers, second scraps, GATE 1-3, DRAFT publication, PROTOTYPE verdicts, Interrogate size, UNPROVEN wire-format facts, and gap triage (fix/drop/rewire vs proceed), is auto-decided the same way. A leaf you launched never returns `NEEDS-USER`; it takes the recommended answer and logs `ASSUMED` itself. One that returns `SCRAP` is checked against architect Phase E's three gates; only a passing SCRAP runs the re-arena (runners are your leaves). A failing SCRAP is logged `ASSUMED: scrap declined` and fill-in continues. Append every auto-decision and your DONE summary to the log before ending your turn, and each created issue's URL/ID (map, spec, tickets: draft number -> ID) to `state.md` the moment its create returns. Write your log before you Read it. Do not Read the relay log, `must-clear.md`, or `report.md` until you have written that file. Product Reads and edits happen only inside the ticket or integration worktree named in the brief. The main checkout is not that tree. Wait for a deploy with one `railway logs`, not a sleep loop of `railway deployment list`. Every turn-ending message starts with exactly one tag, and you first overwrite `<your log minus .md>.last.md` with it verbatim:
- `WAITING <leaf ids>`: leaves still run and nothing else can move; you are re-invoked when they finish.
- `PROTOTYPE-LOGGED`: prototype run instructions + verdict appended to the log; run continues.
- `DRAFT-PUBLISHED`: draft auto-published (seams/slices, URLs/IDs); draft file kept for post-hoc correction.
- `CHECKLIST`: only for hard blockers (failing command + error, steps only the user can take, facts to report back). If the steps capture any value or span 2+ stages, follow `wizard` (script at `<scratch>/wizard-<name>.sh`) and list its run command; the user replies `done` or variable names, never values, so none enter the relay log.
- `DONE`: settled decisions, ASSUMED list (every auto-taken decision with one-line reason), artifact pointers."

## Autonomous mode (default) + interactive opt-in

Default is `autonomous` (this file). Record `mode: autonomous` in `<scratch>/state.md` and every lead brief.

In `autonomous`, auto-decide everything with `ASSUMED: <question> -> <answer> (<reason>)` in the log, and continue without ending the turn:
- GATE 1 destination: auto-confirm the lead's recommendation, continue to Phase 2. Keep the DONE summary in the log for post-hoc correction.
- GATE 2/3 DRAFTs: auto-publish per Phases 2-3, keeping draft files for post-hoc correction (do not delete).
- Slug exists: resume only when the mode value is `autonomous` or `interactive` and equals this invocation, and path/destination match. Read the value, ignoring a leading `-`. Any other value, a missing mode, or a mismatch continues as `<slug>-2` with rebuilt `state.md`. Never ask.
- No-fog → Path B switch: auto-yes, set `state.md` path to B, charting logs count as Path B's conversation.
- Between tickets: continue, name closed/next in the log and at the next user-visible stop.
- Interrogate size prompt: auto-decide by triage (no auth/wire/shared-code signal → decline; else run), log `ASSUMED`, continue.
- Phase 4 with gaps: auto-triage — fix AFK when fixable, else gap (triple-red gaps immediately), rewire around gapped tickets when possible, proceed with the partial set. Never ask fix/drop/rewire vs proceed. `DONE` carries landed/gapped counts.
- UNPROVEN wire-format facts: log as proven-risk in the report, continue. Never merge-block.
- `PROTOTYPE-READY`: log run instructions + verdict, continue. Never wait for UX judgement.
- Docs/non-functional gaps touching no public surface and any other routine gap: gap and proceed.

Report in `autonomous`: print every `ASSUMED` line grouped by phase at the end of `report.md`; `DONE` carries landed/gapped counts.

Interactive opt-in: invoke as `ship it interactive`. Record `mode: interactive` in `<scratch>/state.md` and every lead brief. In `interactive`, restore the old behavior: relay low-confidence grilling questions, GATE 1-3 approvals, between-ticket go-aheads, Phase 4 completion and Interrogate-size `ROUND`s, and `PROTOTYPE-READY` waits verbatim to the user. Re-invoke past runs with `interactive` do not retro-apply approvals to already-published artifacts; corrections go through fresh leads per Phases 1-3.

## Route (in-session, no subagent)

Read the target SKILL.md before each phase; summaries here are a cache.

1. Preconditions. If one fails, stop and tell the user what's missing (hard blocker, the only stop in Route):
   - `git rev-parse --show-toplevel` succeeds. With no repository, ship-it doesn't apply: point the user at the `grill-me` skill.
   - `docs/agents/issue-tracker.md` exists and names GitHub, GitLab or local markdown. Any other tracker's doc must give the commands to create, fetch, comment on, label, close and block issues (Path A also: child link, claim, frontier query, per wayfinder's Wayfinding operations). Otherwise attempt the `setup-matt-pocock-skills` repair AFK; stop only if it cannot be repaired AFK. This overrides wayfinder's local-markdown fallback.
2. Pick exactly one sharpening path:
   - Huge, foggy, greenfield, destination unclear, larger than one session holds → Path A (`wayfinder`: chart map, work tickets until clear, merge at `to-spec`).
   - Holdable in one session → Path B (`grilling` + `domain-modeling`, what `grill-with-docs` runs; both are model-invoked, so the lead can load them).
   - Conversation already holds settled decisions (cleared map, finished grilling) → write them to `<scratch>/relay-sharpen.md` as a `DONE` summary, set `state.md` path to A if a map is cited, else B, then skip to Phase 2.
3. Fix `<slug>` now, once: the kebab-case name of the effort (also `to-tickets`' `<feature-slug>` and `implement-spec`'s `<spec>`); if `.scratch/<slug>` or `.scratch/<slug>-map` already exists, resume only when its mode value is `autonomous` or `interactive` and equals this invocation, with matching path/destination (read the value, ignoring a leading `-`; then update `state.md` and fresh leads per relay step 5 for the first unchecked phase, in Phase 1 the `relay-sharpen*` log whose last tag line is not `DONE`, else the map frontier). Missing `state.md` (rebuild from the logs), any other mode, or a mismatch: continue as `<slug>-2` — never ask. `<scratch>` is the absolute path `<repo-root>/.scratch/<slug>` in the main checkout; briefs always pass it absolute, since leaves work in worktrees. On a local tracker, Path A's wayfinder `<effort>` is `<slug>-map`, so map tickets (`.scratch/<slug>-map/issues/`) never collide with build tickets (`.scratch/<slug>/issues/`).
4. Write `<scratch>/state.md`: mode (`autonomous` default, or `interactive` when invoked with `interactive`), slug, path, and a checklist Route / Sharpen / Spec / Tickets / Implement / Review. Add pointers as they appear (map URL or wayfinder effort, spec URL, ticket IDs, `$INTEGRATION` and its worktree path, `BASE`, check commands, PR URL, must-clear path, gaps dir). Update it at every phase end. It is the run's todolist and its handoff between phases.
5. Labels (GitHub/GitLab only): a create with `--label` fails on a missing label. Before the first publish that needs one, create whichever of these is missing (`gh label create <name>` / `glab label create --name <name>`; an already-exists error counts as success, so no list is needed): `ready-for-agent` and `ready-for-human` (spelled per `docs/agents/triage-labels.md` when it exists; every brief carries that path, and role names in this file and the cited skills map through it), plus on Path A `wayfinder:map`, `wayfinder:research`, `wayfinder:prototype`, `wayfinder:grilling`, `wayfinder:task`. `blocked-by-gap` and `blocked-by-gap-candidate`: ensure per `~/.config/opencode/references/flag-routing.md` before the first Status write.

## Phases (one lead each, sequential; no HITL gates in autonomous)

Phases 1-2 rule, both paths: a lead that edits `GLOSSARY.md` or an ADR does so in the integration worktree and commits there before returning. It creates `$INTEGRATION` and its worktree per `implement-spec` step 3 if absent, and records both in `state.md`. It never commits to the default branch. While `$INTEGRATION` exists, every Phase 1-2 lead and leaf reads and edits those files in that worktree (briefs pass the path), so a later lead sees earlier edits and Phase 4 worktrees inherit them.

### 1. Sharpen (lead depth 1; research leaves depth 2)

- Path A: the lead follows `wayfinder/SKILL.md` as reference. Chart once (auto-decide both charting grills; the destination must end in a spec for `to-spec`, and an in-place change or bare decision is logged with `ASSUMED` and continued; if charting finds no fog, auto-switch to Path B, set `state.md` path to B with the charting logs counting as Path B's conversation), then one fresh lead per follow-up ticket, which creates its relay log before claiming. The charting lead's research tickets run as depth-2 leaves, each in its own worktree (push its branch only when there is a remote); each returns its answer and Decisions-so-far line to the lead (on every tracker the leaf never comments on, edits or closes the ticket; the charting lead posts the resolution comment and closes it, in the main checkout on a local tracker), which appends those lines to the map one at a time. A later research ticket's own lead may fan out `research`'s angles as depth-2 leaves. Grilling/prototype tickets run autonomously under that ticket's own fresh lead, which after auto-deciding the answers posts the resolution comment, closes the ticket and appends its Decisions-so-far line to the map. A prototype stays on a throwaway branch or worktree linked from the ticket by branch name (local: a line in `## Answer`); it never touches real code or main (overrides `prototype` step 6, which assumes an implementation issue), and its verdict goes in the resolution comment plus the relay log as `PROTOTYPE-LOGGED`. Task tickets: attempt AFK first; only genuinely human-only steps with no AFK path become a hard-blocker `CHECKLIST`. Between tickets, log the ticket that closed and the next one and continue without waiting. Exit when no open tickets remain and no fog is left. An empty frontier with open tickets still blocked is auto-triaged (rewire or gap, log `ASSUMED`).
- Path B: the lead follows `grilling` and `domain-modeling`. Done when it returns `DONE` (frontier empty, all decisions auto-taken with `ASSUMED` lines).
- GATE 1: auto-confirm. The lead's `DONE` summary (Path A: compiled from the map's Decisions-so-far) is logged with `ASSUMED: destination confirmed (autonomous)` and Phase 2 starts immediately. A user correction volunteered later is appended as `CORRECTION: <text>` to the Phase 1 log and handled by a fresh Phase 1 lead from the logs (Path A: a new wayfinder ticket or charting re-grill; Path B: resume grilling), then Phase 2 re-runs.

### 2. Spec (lead depth 1, spawns nothing)

The lead follows `to-spec/SKILL.md` as reference. Path A: the brief points at the map (`to-spec` step 1 reads it). Path B: every `relay-sharpen*.md` log is the conversation to synthesize. Skip only `to-spec` step 2's user check; still sketch the seams. Write `<scratch>/spec-draft.md`, create missing labels per Route step 5, and publish per `to-spec` step 3 (one spec issue, `ready-for-agent`). Keep the draft. Log `DRAFT-PUBLISHED` (seams, URL, draft path) only after the issue exists; that tag ends the turn. Done when the spec is published and its `DONE` reports the URL; record it in `state.md`. The approved seams are the run's confirmed test seams (Phase 4). An overturned assumption discovered later is fixed by the lead with any affected glossary or ADR.

### 3. Tickets (lead depth 1, spawns nothing)

The lead follows `to-tickets/SKILL.md` as reference, running its grep-clean gate on the drafts. There is no approval step. On GitHub/GitLab the spec issue (`state.md`) is the source issue, so published tickets become its sub-issues. Write one draft per ticket to `<scratch>/tickets-draft/<NN>-<slug>.md`, numbered blockers first, with `Blocked by:` written in those draft numbers and every `Both:` set to `no` (no sketch exists yet to cite; `implement-spec` step 4 arbitrates). Grep-clean, then publish per `to-tickets` §5 (blockers first, `ready-for-agent`, draft numbers rewritten to real IDs in the second pass, then re-run grep-clean on each published body). Keep the drafts. Log `DRAFT-PUBLISHED` (slices, URLs) only after every ticket issue exists; that tag ends the turn. Never end on `DRAFT`. Done when the drafts are published and `DONE` reports ticket URLs/IDs blockers-first; record them in `state.md`.

### 4. Implement (lead depth 1; leaves depth 2)

The lead follows `implement-spec/SKILL.md` steps 1–6 as reference on `integration/<slug>` (`$INTEGRATION`); steps 7–9 belong to Phase 5. A Phase 1-2 lead may have created it already: reuse it, and if it has no commits ahead of the default ref, run `git fetch origin <default-branch>` (with a remote) and then `git -C <its worktree> merge --ff-only <default-ref>` first. At step 3 the lead records `$INTEGRATION`, its worktree path, `BASE` and the check commands in `state.md`. Its leaves (each brief carries the leaf line above plus `$INTEGRATION`, the absolute `<scratch>` and the spec URL, whose seams are confirmed): one implementer per frontier ticket (`implement-spec` step 4) and one merger at a time (step 5), briefed with the integration worktree path.
- Mergers: a merger that ends without landing resets that worktree to the pre-merge HEAD the lead recorded before launching it (`git rebase --abort` or `git merge --abort` if one is in progress, then `git reset --hard <sha>` and `git clean -fd`, never `-x`; as `resolving-merge-conflicts` step 3 expects). The lead checks `git status --porcelain` is empty before the next one, and, with a remote, after each landing pushes `$INTEGRATION` per `implement-spec` step 3.
- Trade-offs: a leaf hitting a merge or rebase conflict follows `resolving-merge-conflicts` and returns each trade-off it notes in its handback. The lead auto-decides each (log `ASSUMED`), appends each to `relay-implement.md` at once, and copies it to `<scratch>/must-clear.md` once the ticket lands through its merger (a gapped ticket's go in its gap file).
- Flagged tickets: flag routing per `implement-spec` step 4, but the lead runs each flagged ticket's architect or arena step itself (read `architect/SKILL.md` / `arena/SKILL.md` as reference, never via the Skill tool; they are user-invoked). Runners, judge, arena's coherence reviewer and interrogate reviewers are its depth-2 leaves, grounding is read serially, and one implementer then fills the settled sketch. An architect Both-signal makes the lead write `Both: yes` with its cites and arbitrate per `implement-spec` step 4 at once; an active holder's code-arena replaces the filling implementer.
- Commits: the lead commits an arena result (`Arena: yes`, or `Both`'s code-arena) or a scaffold to a ticket branch it creates in its own worktree from `$INTEGRATION` (`Arena: yes`: from the tip SHA named in the candidates' brief, even if `$INTEGRATION` has moved, so the ff-only below holds), and records each commit SHA in `state.md`. `Both` keeps that one worktree and branch through scaffold, code-arena and verify. Candidates fork from the scaffold SHA (`Arena: yes`: the `$INTEGRATION` tip SHA, named in the brief) and never rebase. The pick lands by `git merge --ff-only` of the base candidate's branch onto the ticket branch, with grafts hand-folded and committed on top. Drift against `$INTEGRATION` is handled when the branch lands (step 5).
- Worktrees: the lead removes a worktree (`git worktree remove --force`, then `git worktree prune`) only once `git -C <wt> status --porcelain` is empty or its contents are deliberately discarded (runner and candidate worktrees after the pick and graft are committed and the synthesis note written). Their branches are deleted by arena Outputs; every other branch survives.
- Landing and red: an `Arena: yes` or finished `Both` branch lands like any implementer's (step 5). A scaffold branch is first taken at its tip by the filler, or after a first red with no implementer to message by a repair implementer. A fresh implementer after a second red takes a new branch from the recorded scaffold SHA (`Arena: yes`: arena result SHA), so the lead's commit survives and no branch is shared. This overrides `implement-spec` step 4's branch-from-`$INTEGRATION` for lead-committed tickets. The failed implementer's worktree is discarded in Phase 5.
- Bookkeeping: the lead appends `SCRAP <ticket> #n` to `relay-implement.md` per architect scrap it handles; a resumed lead counts them. It spawns the exploration subagent, or runs the swarm when `implement-spec` step 2 triggers it (read `swarm/SKILL.md` as reference, never via the Skill tool); its workers are leaves. Test seams: the spec auto-published in Phase 2 lists the confirmed seams, which satisfies `tdd`'s confirm step. Any other seam is auto-decided by the lead with an `ASSUMED` line and continued. An architect checkpoint the lead hits itself is auto-decided the same way.
- Write the must-clear list to `<scratch>/must-clear.md` as entries arrive. Triple-red tickets gap per `implement-spec` step 5 (log `ASSUMED: gapped after triple-red`, continue).
- Done when every ticket is landed, gapped, `blocked-by-gap`, or waiting behind a gapped ticket — auto-triage gaps (fix AFK when fixable, else gap/rewire, proceed with partial set, spec left open, gaps listed in the report). `DONE` reports the PR URL (if any), must-clear path and gap paths; record them in `state.md`.

### 5. Review and close (lead depth 1; review and fix leaves depth 2)

The lead works in the integration worktree (`implement-spec` step 3; a branch can be checked out in only one worktree) and runs `dev-code-review` with `BASE` from `state.md` as the fixed point and the spec URL from `state.md` as its §2 spec source (it never asks the user for the spec); the axis reviewers and any gate reviewers are its depth-2 leaves, each briefed with the worktree path from `state.md` as its cwd. Append each leaf's output to `relay-review.md` as it returns; the Blast-radius writeup goes under `## Blast-radius` there, and that is the writeup path to report. The Interrogate size prompt is auto-decided by triage (no auth/wire/shared-code signal → decline with `ASSUMED`; else run). Then, serially:
1. Fix the review issues and every `<scratch>/must-clear.md` entry (`implement-spec` step 7); its implementer and the merger that lands the fix (step 5 gate) are leaves, and you never edit `$INTEGRATION` yourself. Review issues are Spec findings, violations of documented repo standards, Interrogate Act On and proven Blast-radius Risks; all other review output goes in the report for the user. After the merger lands, push `$INTEGRATION` (`implement-spec` step 3, with a remote), re-run the step-3 check commands and re-check each fixed finding; a fix still red after three tries (any red, at the merger gate or this re-check, counts; same implementer, then a fresh one, as in `implement-spec` step 5) is gapped with `ASSUMED` and listed in the report — never a `ROUND`.
2. An UNPROVEN wire-format fact in the Blast-radius writeup is logged as proven-risk in the report — never merge-blocking. Mark the draft PR ready (body via `pr`, keeping its `Closes` lines) or resolve the landed tickets per the tracker (`implement-spec` step 8; gapped and blocked ones stay open).
3. Write the Report below to `report.md.tmp`, then `mv` it to `<scratch>/report.md`, with paths as they stand now. A fresh lead that finds `report.md` resumes at step 4 and never re-reads tickets (GC empties `issues/`).
4. Clean worktrees (`implement-spec` step 9, plus every other worktree but the integration one: runner, candidate, swarm, research-leaf and abandoned implementer; each only once `git -C <wt> status --porcelain` is empty or its contents are logged as discarded, then delete candidate/runner/swarm branches, never `$INTEGRATION` or a ticket branch with unlanded work), then GC scratch per `setup-matt-pocock-skills/issue-tracker-local.md` §scratch GC convention (keep `blast/` until `$INTEGRATION` is merged or gone, and when merge cannot be confirmed keep it and list it), appending every moved or deleted path to `report.md`.
5. Return `DONE` with the report.

Never merge `$INTEGRATION` into the default branch and never delete it: it is pruned only after the user merges it (`implement-spec` step 3). Done when the must-clear list is empty, review issues are closed or gapped with `ASSUMED` reasons, and `report.md` is written and returned in `DONE`.

## Report

Map link, spec link, ticket count, `$INTEGRATION`/PR link, blocked/gap IDs + paths, review items left for the user, corrections path + count, blast-radius writeup path, check commands that were missing (e.g. `typecheck: none`). Append every `ASSUMED` line grouped by phase. One line per artifact, names not bare numbers. Paths are as they stood before GC; the GC log at the end of the report says where they went.
