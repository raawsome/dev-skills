# Flag routing (canonical)

Single source for `Architect:` / `Arena:` / `Both:` criteria, Both arbitration, grep-clean, corrections, and the `blocked-by-gap` lifecycle.

`to-tickets` marks flags before publish. `implement-spec` step 4 re-checks flags and writes later `Both:` / `Status:` transitions (`implement` re-checks flags only). Cite this file; do not restate.

- `Architect: yes` when the interface, usage, or module shape must still be settled before implementation, `no` otherwise.
- `Arena: yes` only when `Architect: no` AND the implementation approach itself is high-uncertainty or hard to reverse, with 2+ concrete approaches under a settled interface (a shared seam, 2+ data-flow or state-ownership shapes). `No` on everything else — including every `Architect: yes` ticket, since architect already runs an internal arena over sketches in its Phase B.
- `Both: yes` only as a narrow escape: when the architect Phase C synthesis decision still names 2+ cited hard-to-reverse implementation approaches after the sketch settles. Each counted approach cites its sketch section plus a distinct axis (API shape / data model / failure semantics / external contract) plus a 1-line reason; variants without an axis diff do not count. The arbitration rubric below is the only `Both:` gate. Both cap: 1 active + 1 queued per spec; Both code-arena N=3 default, N=5 only with arena Phase A criteria cite. The holder self-marks Both: active <its-own-ticket#> in its own flag line; the next holds Both: yes (queued, reason: <2+ approaches + what is hard-to-reverse>). Transitions (vacate / promote / re-enter / downgrade): see arbitration table below (re-enter as Both: yes, re-arbitrate). Blocked: means dependency-blocked, distinct from Status: blocked-by-gap and the Blocked by: body field. `to-tickets` writes `Both: no` (no sketch exists yet to cite); `implement-spec` step 4 writes every later `Both:` marker and `## arbitration` entries; any consumer appends `## corrections`; `Status:` belongs to implement-spec step 4. Re-score budget and promotion order: see arbitration table below (re-entry is budget-free).

Both arbitration (canonical — consumers cite, do not restate): filter to frontier-ready first; blocked claimants keep flags untouched and hold no slots (they enter the next scoring pass on unblock, subject to the cap); when none is ready, defer scoring until one unblocks (leave flags, note the deferral). Otherwise score ready tickets by `score = Rmax × f(n_raw)` where `n_raw` is the cited approach count, `f(n_raw)`: 2→1.0, 3→1.2, ≥4→1.3; `Rmax` is the max cited hard-to-reverse weight (b-scale, each band cited to the current-spec synthesis section ID: 1 reversible <1d refactor no migration, 2 costly 1–5d migration or internal break, 3 hard persisted-data/external-contract break or >5d rewrite). Gate: eligible iff `n_raw ≥ 2` AND `Rmax ≥ 2` (cross-spec or missing cites count as uncited). Uncited or single-approach `Both: yes` claims are ineligible, never auto-fill (holds empty; downgrades to `Arena: yes` linked to the sketch in the same pass). Total-order tiebreak: score desc, then Rmax desc, then n_raw desc, then lowest ticket number (no tie band). Rank top ready-eligible to `Both: active <ticket#>`, next to queued, downgrade the rest to `Arena: yes` linked to the settled sketch ID (downgrades route to `Arena: yes` only; re-escalate only on a newly discovered hard axis with sketch amendment).

Both lifecycle transitions (Both value syntax (canonical): `no` | `yes` | `yes (queued, reason: ...)` | `active <n> [(ex-queued: <reason>)]`; log per the schema below):

| Transition | From → To | Trigger | Flag write |
|---|---|---|---|
| vacate | `active` → empty | holder becomes `Blocked:` (dependency-blocked) | clear slot, log vacate |
| promote | `queued` → `active` | active slot vacated | self-mark `Both: active <ticket#>`, log promote |
| re-enter | `no` → `yes` | unblocked, re-arbitrate in next scoring pass | re-claim `Both: yes`, log re-entry |
| claim | `no` → `yes` | architect Phase C Both-signal on an `Architect: yes` ticket | write `Both: yes` with its cites, log claim, arbitrate at once |
| downgrade | `yes` → `Arena: yes` | ineligible or cap excess | downgrade, set `Both: no`, log `→Arena` |

Log `ticket#, a=n_raw, Rmax, score, N, Active|Queued|→Arena, one-line reason` per decision under `## arbitration` in `.scratch/<spec>/flag-corrections.md` (N = code-arena size, 3 default; 5 only with arena Phase A criteria cite; N optional, defaults to 3 for 6-tuple readers), which has two sections, `## arbitration` (per-decision Both scoring logs) and `## corrections` (normalizer/gap fixes).

Flag criteria are canonical in this file. Consumers cite this file; they don't redefine the flags. Before publishing, require grep-clean: each ticket (its file, or its issue body saved to a file) carries all three ^Architect: / ^Arena: / ^Both: lines outside fenced code; grep-clean passes when ``awk '/^```/{f=!f;next} !f' <file> | grep -oE '^(Architect|Arena|Both): ' | sort | uniq -u | wc -l`` prints `3` (each line exactly once). Rewrite the ticket and re-run this check until clean.

No `Blast:`/`Swarm:` flags by design: wide refactors sequence via §3 expand–contract (:40); blast analysis fires via `dev-code-review` §5 property triggers; multi-slice exploration fans out via `implement-spec` step 2. These route on properties, not flags (properties per blast-radius Escalation rule).

When a consumer (`implement`, `implement-spec` step 4) finds a flag line missing, malformed, or contradicting another flag, it re-checks against the criteria above in one cheap pass:
(1) well-formed contradictions resolve by priority Both > Architect > Arena (the ticket flag wins unless it contradicts the criteria; e.g. `Arena: yes` with `Architect: yes` forces `Arena: no`, except a Both downgrade linked to a settled sketch ID, which stands and runs arena on the bodies), log-not-silent — append each to `## corrections` like (3);
(2) normalizable values per the canonical map (case, surrounding whitespace, strip trailing `./,` punctuation, then `y`/`yes` only) normalize and proceed; well-formed `Both:` values (cited, not restated) proceed without normalize;
(3) an unnormalizable or missing line marks that ticket `blocked-by-gap` — `implement-spec` step 4 writes `Status:`, skips it, and continues the rest of the frontier; a routine ticket missing only an irrelevant line proceeds (missing line defaults to `no`, logged). A syntactically well-formed but ineligible `Both:` claim downgrades per the arbitration rule above, never gaps.
Append each correction to `## corrections` in `.scratch/<spec>/flag-corrections.md` (create the file with empty `## arbitration` and `## corrections` sections if absent) and cite its path + count in the integration report; the PR body carries a one-line count + link. Corrections occurred iff `## corrections` is non-empty; escalate contradictions outside these pairs. `Blocked-by-gap` lifecycle (canonical): implement-spec step 4 alone writes the `blocked-by-gap` `Status:` transitions, skips the ticket, and re-runs the three-line grep each frontier pass — fixed = grep-clean + re-check passes + Both-cap compliant; the clearer (whoever edits the flags) resets `Status:` to ready-for-agent and appends to `## corrections`; the run lead owns the fix request. On GitHub/GitLab, `Status:` is a label: `blocked-by-gap` replaces `ready-for-agent`, and the reset swaps them back. Import matches on gate-failure gaps are `blocked-by-gap-candidate` for lead check, never auto-ready. Before the first GitHub/GitLab `Status:` write, ensure `blocked-by-gap` exists (`gh label create <name>` / `glab label create --name <name>`; already-exists = success). Same for `blocked-by-gap-candidate` when that label is used.
