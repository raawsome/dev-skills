You have been provided a spec. This spec should have tickets associated with it, describing how to implement the spec.

The issue tracker should have been provided to you. If not, tell the user to invoke the `setup-matt-pocock-skills` skill.

The goal is the entire spec implemented on a single **integration branch**, with every ticket resolved the way the issue tracker closes work.

The tickets are not a list of steps. They are a **task graph** with blocking relationships between them. This means there is always a **frontier** of tickets which are ready to be grabbed.

Communication to and from subagents should be sparse. Communicate primarily through **context pointers**: to the spec, tickets, research notes, and previous commits. Cite by path instead of duplicating pointed-to material.

**Implementer subagents** should be run in the background where possible for maximum concurrency.

## Steps

2. (optional) Use an **exploration subagent** to conduct any exploration required by the tickets - relevant codebase files or external documentation. Protocol per research §fanout-depth; payload: run implementer serially in-ticket. Briefs state 'depth: top|child'. Implementers and mergers never fan out. You, the orchestrator of this skill, run each flagged ticket's architect or arena step yourself (read `architect/SKILL.md` / `arena/SKILL.md` as reference, never via the Skill tool; they are user-invoked), so its runners sit one level below you, never below an implementer.

3. Create the integration branch named `integration/<spec-slug>` <!-- CUSTOM-BEGIN: integration-branch, reason: upstream has no $INTEGRATION convention; retirement: delete markers if upstream adds an integration-branch convention -->(`$INTEGRATION`). Pass `$INTEGRATION` in every implementer and merger brief. `.scratch/<spec>` always means the main checkout's folder: pass it as an absolute path in every brief, since implementers and mergers work in worktrees. `<default-ref>` is `origin/<default-branch>` after `git fetch origin <default-branch>`, or the local default branch when there is no remote. Create `$INTEGRATION` with `git branch --no-track $INTEGRATION <default-ref>` (skip when it already exists, e.g. ship-it Phases 1-2 made it; `BASE` still comes from `git merge-base`), never checked out in the main checkout, and give it one integration worktree: mergers land there and the final review runs there. Record `BASE` = `git merge-base <default-ref> $INTEGRATION` for step 7. Record the check commands once, from the repo (package.json scripts, Makefile, CI config, CLAUDE.md): typecheck, ticket-scoped test, full suite, and the source directories; write `typecheck: none` when the repo has none and say so in the report. With a remote, push after the first merge and after every later landing (step 7 fixes too): `git -C <integration worktree> push -u origin $INTEGRATION`, never `--force`; the draft PR needs it. Mergers are leaves, so the push is yours (the orchestrator's) after a merger lands. Never merge `$INTEGRATION` into the default branch yourself. Prune it (local plus remote) only once its PR is merged, `git merge-base --is-ancestor $INTEGRATION <default-ref>` passes, or the user says to: deleting the branch of an open PR closes the PR.<!-- CUSTOM-END --> If the issue tracker closes work through PRs, or the user asks for one, open a draft PR after the first merge in step 5 (a branch with no commits ahead of main can't open one), marked as closing the spec and tickets. <!-- CUSTOM-BEGIN: landed-closes, reason: merging the PR must not auto-close gapped or blocked tickets; retirement: delete markers if upstream scopes closing keywords -->List a ticket as closing only once it has landed, updating the body as tickets land; the spec closes only when every ticket has landed.<!-- CUSTOM-END -->

4. Use **implementer subagents** to implement each ticket, each in its own worktree on its own branch. <!-- CUSTOM-BEGIN: flag-routing, reason: upstream has no ticket flags; retirement: delete markers if upstream adopts routing flags -->Before routing, check all three flag lines (`Architect:`, `Arena:`, `Both:`); re-check per `to-tickets` §4 — contradictions (1) / normalization (2) / gaps (3) — in one cheap pass (cite §4); `Status:` marks + skips per the §4 `blocked-by-gap` lifecycle here.    - `Arena: yes` (which implies `Architect: no` per `to-tickets` §4) goes through **arena** instead of a single implementer.
   - `Both: active <ticket#>` takes the Both path (architect sketch scaffold first, then code-arena on bodies, then verify), queued tickets wait, other claimants route as `Arena: yes` per `to-tickets` §4, the sketch keeps architect Phase C checkpoint rules (per architect Phase C).    - routine tickets: single attempt. Done iff every frontier ticket is either skipped-blocked or routed-once, in a logged table.<!-- CUSTOM-END --> <!-- CUSTOM-BEGIN: both-pick, reason: first-wins is order-dependent; retirement: delete markers if upstream adopts a selection rubric -->Both collision, or a new claim from an architect Both-signal (arbitrated at once): arbitrate per `to-tickets` §4; otherwise apply once per frontier pass after the step-6 frontier check (wave-1: arbitrate the initial frontier in step 4 before routing, no S6 prerequisite).<!-- CUSTOM-END --> Each implementer subagent:
   - <!-- CUSTOM-BEGIN: drift-check, reason: upstream has no pre-start drift check; retirement: delete markers if upstream adds drift handling -->checks drift before starting: `git rev-list --left-right --count $INTEGRATION...HEAD` for magnitude and `git merge-tree --write-tree HEAD $INTEGRATION` for conflict prediction (exit 1 means conflicts; needs git 2.38+); if diverged or conflicted, rebase onto `$INTEGRATION` before calling `tdd`;<!-- CUSTOM-END -->
   - calls the Skill tool with `tdd` to build the ticket;
   - merges `$INTEGRATION` into its own branch before reporting done

5. Once an **implementer subagent** completes, merge its work to the integration branch with a **merger subagent**. <!-- CUSTOM-BEGIN: merger-gate, reason: over-broad grep bounces green merges + WARN/advisory must-clear; retirement: delete markers if upstream narrows the grep or adds a must-clear list -->Run one merger at a time, in completion order: the next merger starts only after the previous one has landed or bounced, and only a merger writes to `$INTEGRATION`. Merger gate is typecheck (must run on every merge and block landing on red) plus ticket-scoped tests (red) plus grep, using the step-3 check commands. DENY regex is scoped to the step-3 source directories (default `src/**`); the patterns below are the TypeScript/JavaScript set, so swap in the repo language's skip and suppression markers: deny `\.skip\(|\bdescribe\.skip\b|\bit\.skip\b|\btest\.skip\b|\bxdescribe\b|\bxit\b|\bTODO\(tdd\)|\bFIXME\(tdd\)|@ts-nocheck` plus the scaffolder markers (`ARCHITECT-NOTE`, `ARENA-NOTE`, `DO-NOT-SUBMIT`). On a second red, launch a fresh implementer on a new branch from the current `$INTEGRATION`, with logs 1–2, for one more attempt, then re-gate (log 3); on third red write `.scratch/<spec>/gaps/<ticket>.md` with gate logs 1–3 plus SHAs plus the old-to-new edge map (edge syntax per `to-tickets`), append `Gap: <that path>` to the ticket (local: its file; GitLab: its description; else a comment), swap its `ready-for-agent` for `ready-for-human` (local: the `Status:` line) so no frontier pass routes it again, land nothing. Tickets that depend on the gap ticket, directly or through other tickets, stay blocked: don't route them, and list them under the gap in the step-6 report so the user decides (fix the gap, drop them, or rewire their edges with the gap file's edge map). Continue the frontier around them. Frontier reporting per step 6 (cite, do not restate).<!-- CUSTOM-END -->

6. If this changes the **frontier** of available tickets, kick off more **implementer subagents** to work on the new tickets. <!-- CUSTOM-BEGIN: gap-recheck, reason: upstream has no blocked-ticket recheck; retirement: delete markers if upstream adds gap handling -->If step 4 skipped any `blocked-by-gap` ticket, each frontier pass re-checks per the `to-tickets` §4 lifecycle; fixed tickets re-enter as ready, cleared automatically on fix. When the frontier empties with gap tickets or their dependents still open, or after 3 consecutive frontier passes with the 'blocked-by-gap' set unchanged, report the blocked ticket IDs plus gap paths to the user, naming requester + clearer so none starves, and continue the unblocked frontier (no new fan-out onto blocked tickets until fixed).<!-- CUSTOM-END -->

7. Once all tickets are complete, call the Skill tool with `dev-code-review` on the integration branch, with the step-3 `BASE` as its fixed point. Interrogate gate per dev-code-review §5 autonomous rule (log suggested interrogation with reason and continue, never block). <!-- CUSTOM-BEGIN: must-clear-fix, reason: upstream has no WARN/advisory must-clear list; retirement: delete markers if upstream adds a must-clear list -->Fix all review issues plus every must-clear entry in a single implementer subagent; done iff must-clear list empty and review issues closed.<!-- CUSTOM-END -->

8. If a draft PR exists, mark it ready for review. Otherwise, <!-- CUSTOM-BEGIN: resolve-landed, reason: closing a gapped or blocked ticket deletes its gap file via GC and unblocks the archive; retirement: delete markers if upstream scopes closing -->resolve each landed ticket (gapped and blocked ones stay open)<!-- CUSTOM-END --> the way the issue tracker closes work, and report the integration branch. <!-- CUSTOM-BEGIN: pr-corrections, reason: upstream has no corrections-count-plus-pr-body rule; retirement: delete markers if upstream adds it -->Corrections per the `to-tickets` §4 iff rule; cite its path + count in the report and carry a one-line count + link in the PR body. When a PR exists or is created (step 3 draft or step 8 mark-ready), call the Skill tool with `pr` to shape the body.<!-- CUSTOM-END -->
